# Reference study 8: interim protocol and static review

Read-only review snapshot: 2026-10-18, after the first nine completed CPU runs (pairs 0–2). This note is outside the active runner's inputs/output. It is not an acceptance result or a substitute for all 84 JVMs and seven paired blocks per workload.

## Protocol sanity

- The prepared manifest declares four workloads, seed 42908, seven blocks, three modes, 30-second warmup and 60-second measurement: 84 fresh JVMs and 7,560 fixed observation seconds.
- The first nine completed run-order entries have distinct child JVM commands, exit 0, mode order randomized inside each block, identical `-Xms256m -Xmx256m -XX:ActiveProcessorCount=4` flags, and the immutable copied classpath. Only instrumented mode adds the prepared startup agent and explicit three-method allowlist.
- Each completed measurement reports warmup 30, requested measurement 60 and actual elapsed between 60.004 and 60.013 seconds. Application operation latencies are explicitly closed loop and omit arrival-queue delay. Instrumented and JFR modes both start the same configured JFR recording before warmup.
- Completed instrumented CPU pairs 0–2 report healthy collection; zero queue drops, shutdown discards, probe failures, method/histogram overflow or duration clipping; and incomplete=false. Their retained timing counts are 1,664,443 / 1,723,144 / 1,909,925. The first 10,000 raw rows are retained and the remaining rows are counted as prefix omission, not event loss. Method registry proves all three selected workload methods were transformed; only the CPU method executes for this workload.
- Agent timing totals and the JFR recording include warmup. The application histogram/operation count concern the measurement phase. They must not be equated as if they covered the same interval.
- The application's GC baseline is taken after warmup, but the ending GC counters are read after JFR stop/dump and settings serialization. Thus the exported GC delta can include that post-measurement work; it does not prove a particular GC happened inside the operation-latency window. RSS is process-lifetime peak, also including setup/warmup/dump.
- The runner rewrites the child settings sidecar from the shared EventCapabilities declaration. Static review confirms that declaration matches WorkloadMain's requested six events, sample period, allocation throttle, contention/park thresholds and stack settings on this supported JDK. It is a requested-configuration declaration; it should not be described as independent proof of every effective JFR setting.

## Partial observations, not gate verdicts

Instrumented CPU paired throughput changes for completed pairs 0–2 are approximately -7.21%, -11.25%, +4.69%; paired p99 changes are +32.51%, +56.50%, +8.59%. JFR-only p99 changes are -13.77%, +28.20%, +50.09%. These are individual incomplete-study diagnostics; no median/uncertainty or acceptance conclusion is drawn here. Baseline p99 itself ranges from 111,807 to 206,335 ns across those blocks. Do not attribute those differences to an observer mechanism from these JSON counters alone.

## Static overhead candidates for later investigation

1. `TimingBuffer.poll()` constructs one Timing record per accepted event. Escape analysis may eliminate some allocations, but that is unproven without later profiling. The consumer processes roughly 1.7–1.9 million events over each 90-second CPU run. A primitive single-consumer drain callback could remove this allocation path while retaining the existing immutable poll API for compatibility; do not reuse a mutable event object across code that may retain it.
2. The consumer checks System.nanoTime and shutdown/disk-budget conditions on every event, performs TreeMap lookup/HDR update, and increments an AtomicLong for each omitted raw row. A bounded batch (for example 64–256 events) could amortize checks and consumer-local counters, while retaining disk checks, shutdown deadline enforcement, exact omitted/drop accounting and bounded batch latency. This is a proposed implementation change only, not an observed speedup.
3. The application probe executes two clock reads, volatile enabled checks, ThreadLocal reentrancy get/set operations, tail CAS and release/acquire sequence traffic. These are real fixed per-selected-call costs. Reentrancy protection, recoverable-fault isolation, bounded nonblocking offer and true per-call timing must remain intact. Removing them to meet a threshold would change the required behavior.
4. Producer and consumer each compute a long remainder by runtime capacity. An explicit power-of-two mask fast path could preserve support for arbitrary configured capacities and reduce common-case arithmetic. Tail/head/sequence cache traffic and false sharing may also matter. Their actual contribution is unmeasured.
5. Added try/catch/probe bytecode may affect JIT inlining or compilation decisions. Consumer wakeups, JFR sampling and allocation can affect scheduling/GC. None is established as the cause of the partial p99 differences. Investigate only after the coordinator releases the quiet interval.

No source, workload, protocol, allowlist, active manifest or active output was changed. No JVM, Maven, Docker, profiler, JFR parser or large artifact hash was launched for this review.
