# IndexForge next ranking experiment — dev/validation only

This is a proposal, not an implemented or measured new model. No Java/Maven/Docker, training, source writes, heldout query/label inspection or final-output inspection occurred. Fixture rows were filtered by the `development`/`validation` split before any query/judgment content was displayed. The local `ranking-devval-only.json` contains exactly 60 allowed queries and their 540 existing build24 CODE_HIGH development/validation ablation rows. Frozen source inspection was limited to documents relevant to these allowed queries, plus generic indexing/query code. Source paths below identify evidence/examples only; they must never become scoring priors.

The .75 nDCG@10 / .90 identifier-MRR targets apply to final heldout acceptance. Validation observations inform development/selection and do not decide final acceptance. Heldout remains unopened; no metric improvement is predicted here.

## Recommendation

Try a syntax-gated query planner before a new learned model. Preserve CODE_HIGH's existing single-identifier/exact-symbol behavior and explicit Boolean/phrase/field semantics. For *plain unfielded multiword* queries only, test removing the identifier/symbol scoring channel while retaining content/prose/concepts/code hints. Use actual query syntax, never the fixture `type` field or a query ID. This directly addresses observed ablations with one general rule rather than another topic catalog.

Keep one bounded pairwise linear LTR challenger behind that gate if the simpler candidate still misorders documents that are already retrieved. Prefer shared query/document interaction features and a tiny frozen hyperparameter set. Avoid document/project/category priors, raw token IDs as learned dimensions, per-query rules or a large tree/neural model on only 40 development queries.

First obtain a label-blind top-500 candidate/feature audit. Top-20 misses alone cannot distinguish absent candidates from a low reranking position; training must not silently insert judged answers into the serving candidate set.

## Preregistered candidate set

Freeze the candidate list, field/feature definitions, fold allocation, seed, optimizer limits and selection rule *before* running it. Treat prior validation exploration candidly: those 20 queries are already repeatedly consulted, not a fresh test set.

- C0: exact frozen CODE_HIGH/SOURCE_AWARE comparator, with current candidate retrieval and no new weights.
- C1: same model and retrieval bounds; runtime syntax gate disables identifier/symbol scoring only for plain unfielded multiword input. Preserve current single-identifier behavior. Explicit Boolean operators, phrases, fields, grouping and unsupported syntax use the existing semantics. No label-derived query type is read by production.
- C2: C1 plus a linear shared-feature reranker on authorized candidates. Start with prose-only activation so a first learned experiment cannot silently degrade the fixed navigational path. If identifier reranking is later proposed, register it separately with concrete query-conditioned features; do not learn a global preference for the benchmark's main project.

Do not select a different candidate for individual validation queries. Do not mix existing per-query results into a synthetic claimed score for C1/C2. They require real complete runs, including stable tie ordering, all ablations, permission/cache/cursor controls and operational measurements on the actual selected artifact.

## Feature representation and bounded implementation

Use at most 24–32 scalar features, all query/document interactions rather than raw identity. Freeze definitions and normalization. Examples:

1. log1p field scores from content, stemmed prose, identifier/symbol and source API-topic channels; normalize within the authorized candidate query or by a development-only scaler, then clip fixed ranges.
2. Exact full declaration equality and split-identifier equality versus partial-token matches. Raw symbol/path strings are not learned dimensions; a path-stem equality test is allowed only as equality with the actual query, preserving the current navigational channel.
3. Distinct normalized query-term coverage, preferably IDF-weighted with a bounded weight cap; retain an unweighted control. Do not add ten more copies of correlated field scores.
4. Maximum coverage/proximity in one bounded source-method/block window versus scattered file-wide mentions. Use preindexed bounded metadata/term vectors; avoid loading 1MiB source into every one of 500 rerank candidates.
5. Per-topic query/document alignment for the existing ten generic JDK/Lucene hint families, with two distinct supported query terms. Distinguish support within one topic from unrelated terms pooled across topics. No arbitrary document or query string catalog.
6. Relative evidence from executable tokens, declarations and comments/literals, rather than a global `isTest`/`isMain`/project-path boost. A query match in a real body versus quoted example is a shared interaction; file role alone is a document prior and is excluded.

No project/repository/document/query IDs, path prefixes, package names, exact class names as learned dimensions, source hashes, output rank labels, annotation-derived answer flags, raw bag-of-word ID weights or frozen fixture lookup features. No independent document intercept/latent vector. Query/document overlap comparisons are permitted; memorizing a particular term-to-file pair is not.

All candidate retrieval/feature lookup stays behind tenant/repository authorization and permission-version checks. Keep the 500 candidate bound, 64 query-token and existing expanded-clause quotas. At 32 features and500 candidates the linear scorer uses16k feature multiplications; query-term extraction and bounded indexed lookups add separate work. This is not a guarantee that p95<200ms. Cached responses and cursor context must bind the exact model/scaler/feature-version digest; a stable profile name alone is insufficient after trained weights change. Reindex if new fields/term vectors change the schema. Explanations expose only authorized-document feature contributions; do not export hidden-repository corpus statistics.

## Pairwise versus listwise learning

A regularized linear pairwise model is the first sensible LTR baseline here. For pairs with graded relevance gi>gj, minimize stable logistic loss log(1+exp(-(s_i-s_j))) plus L2 regularization. Weight by a fixed graded-gain difference and normalize each query's total contribution so large candidate sets do not dominate. Use fixed-seed bounded pair sampling (for example <=512 pairs/query, balanced across available grade contrasts), <=100 iterations, explicit finite-value/convergence checks and a recorded hard wall/memory budget. A failure to converge is a failed candidate, not an excuse to silently change the optimizer after validation.

Group normalization/scaling and regularization are fitted on DEVELOPMENT only. Use a fixed tiny L2 grid {.01,.1,1}, keeping C0 as fallback. No labels are consumed when generating serving candidates; do not inject missing positives into candidate lists. Unjudged candidates can use the frozen evaluation convention for grade0, but record that convention and inspect hard negatives without relabeling them.

Listwise softmax cross-entropy with normalized graded gains is also bounded and avoids quadratic pair generation, but with only40 queries it can overfit a few positive documents/families and does not directly establish nDCG@10 or MRR. LambdaMART/deep models add capacity without enough independent groups. Do not run all learning families as an open-ended validation search. If a listwise challenger is authorized, register it in advance as an alternative to the pairwise run, with the same feature/candidate/regularization/budget constraints, not a new post-result rescue round.

## Structural alternative if the audit shows representation gaps

Do not start by extending a query-to-answer synonym list. Two development-grounded, reusable structural experiments are content-addressed write reuse and checked/bounded input consumption. A bounded same-method relation could detect a digest-derived path, existence guard/early return and otherwise a write, or a byte-count/limit check before accepting another read chunk. A one-hop source-call graph can propagate *generic features* through wrappers such as a digest or durable-file helper; it must not propagate grade labels or reward a named fixture class.

These require meaningful positive/negative counterfactuals: comments/strings, same API names on unrelated receivers, a limit checked only after allocation, existence without verified contents, and an unconditional write that lacks reuse. If the bounded lexer cannot establish receiver/scope relations, abstain or label the feature merely lexical. A mature parse-only Java AST is an option under explicit resource limits and no attribution/compilation/processor execution; it is a larger change and not justified by the current run alone. Declarations alone must not be called proven working behavior.

Prefer this small source-feature branch over LTR only when the candidate/feature audit demonstrates that the current representation fails to expose such relations. Otherwise, the observed prose identifier-overweight problem should be tested first. Neither route guarantees the hard targets on ambiguous context-free identifiers.
