Status: design checkpoint; no implementation or execution authorized here. Build25 is committed as `8de23c7`. This directory is a separate working proposal, not release evidence.

## Inputs and limits

The audit filtered `.work/A06/ranking-devval-only.json` to `split=development` before inspecting query text/grades. `dev-inputs.json` contains those 40 existing DEV queries, the already exported label-blind build25 candidate vectors, and 120 already recorded SOURCE_AWARE rows for C1/D1/C2, filtered to DEV. `dev-source-pairs.json` decodes frozen corpus bodies only for DEV targets or their recorded competing candidates. Paths and query IDs in this note provide provenance; they are prohibited inference/training features.

This is source inspection and extraction of existing facts, not a new ranking evaluation, optimizer run, metric computation or corpus relabeling. The source bodies are the frozen authored evaluation corpus, not current production implementations. In particular, the corpus SafeSourceReader still contains the historical materializing walk that was fixed in production before build17. Its presence does not describe build25 runtime behavior. Unknown judgments remain unjudged under the declared pooled-gain policy.

The permitted existing DEV inputs are:

- `ranking-wave2-build25-attempt1/audit/features.tsv` (40 DEV queries; current ten-dimensional shared-v1 features; original rank is C1/D1 candidate order).
- `ranking-wave2-build25-attempt1/fit/report.txt` and `l2-1.0-fold-*-paths.tsv` (already fitted grouped-DEV diagnostics). Fold path files contain returned prefixes; absence there does not mean absence from the full 500-candidate pool.
- The DEV-filtered SOURCE_AWARE C1/D1/C2 rows from `validation/per-query.tsv`. C2 all-DEV fitted results are in-sample and are not used as generalization proof.
- Source bodies selected from the immutable `fixtures/corpus.tsv`, using only DEV target/competitor paths.
- Existing extractor implementations SearchFeatures, SearchFeatureSchema, CodeFeatures and DeclarationScanner.
- Four actual source entries from the pinned JDK25 `lib/src.zip`, inspected as documentation provenance: MessageDigest, Files, FileChannel and CharsetDecoder. No documentation catalog was generated or executed.

No heldout per-query output was read for this audit. VAL examples, VAL diagnostics and either final experiment's ablation results are not design inputs. Prior aggregate final outcomes remain historical disclosures, not a model-selection signal. This separation cannot undo prior repeated test exposure, which must remain disclosed.

## What the existing vectors cannot express

shared-v1 is primarily lexical: transformed candidate/content/prose/identifier/path/topic scores, global document prose overlap/density/phrase, and exact declaration equality. CodeFeatures detects bounded lexical JDK/Lucene patterns across the whole file. It removes comments and strings and abstains on some type shadows, but does not establish receiver identity, a shared value, membership in the same method, or guard ordering. Pairwise lane reweighting cannot recover a relation missing from all ten inputs.

Existing stored grouped-DEV results support trying a new representation rather than extending the optimizer. L2=1 won the fixed DEV objective with stored OOF nDCG .7311403168018562 and identifier MRR .925, versus D1's stored .7066751871276543/.925. L2=.01 failed its bounded optimizer in fold2; this failure stays preserved. This proposal does not extend that optimizer or recompute those scores.

A feature extractor must expose its limits rather than turn desired labels into “verified” operations.

## Bare identifiers: no defensible hidden-intent fix

The remaining DEV single-name mistakes are `bytes`, `put` and `bounded`. Both the first result and grade3 target contain genuine implemented exact-name declarations, and both have declarationMatch=1 and full single-token coverage in the current vectors. In the frozen source, Model.bytes clones a byte array, SnapshotManifest.bytes serializes a snapshot; DecisionController.put inserts a non-null map field, ContentAddressedStore.put stores source bytes; SnapshotManifest.bounded guards a metadata integer, SafeSourceReader.bounded limits an input stream. All are real declarations.

Exact AST declarations can correct false declaration detection, but do not distinguish these equally exact meanings. The query provides no parameter type, owner, domain or action. No global main/test/helper/public/static/body-length/project/role preference is warranted. This draft therefore preserves build25 single-identifier and explicit-query behavior. It is an experiment on prose representation, not a claim to solve the complete joint quality goal. A future identifier experiment needs independently justified query evidence, not the knowledge of which frozen grade3 file is desired.

## Candidate design decision

Try one finite representation wave: (R0) unchanged C1; (R1) max member-local executable overlap plus actual JDK API documentation overlap; (R2) R1 plus four generic, query-anchored value/receiver/control-flow features. R1 controls whether any effect comes merely from extra API prose. R2 must beat that control on grouped DEV and pass the frozen joint selection guards. The draft below restricts helpers to one unambiguous call within the same compilation unit; q14's cross-file verification chain is intentionally outside the first proof boundary. There is no arbitrary custom-class summary table or new query-to-topic synonym list.

No source edits, models, new feature outputs or new metrics have been produced. The detailed preregistration remains DRAFT until coordinator review and an explicit implementation/execution grant.

The conservative binding policy also limits expected API coverage: many frozen targets use wildcard imports, and parse-only trees cannot establish arbitrary external or same-package types. An unresolved wildcard receiver must abstain rather than be called a resolved JDK API. Member-local lexical coverage can still exist, but no proposed structural/API advantage is assumed for these cases. Whether that conservative first version has enough useful evidence is a design-review question, not a reason to loosen resolution after seeing scores.
