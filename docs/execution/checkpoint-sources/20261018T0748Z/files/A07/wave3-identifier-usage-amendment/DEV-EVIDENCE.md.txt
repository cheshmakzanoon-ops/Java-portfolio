# DEV-only amendment: query-conditioned member usage

Status: OFFLINE AUDIT / DRAFT, no implementation or scores. The original `.work/A07/wave3-representation-audit/**` packet remains immutable. This amendment supersedes its identifier-preservation proposal only if root approves it and a complete new protocol is frozen before execution. No Java, training, new metrics, VAL inspection or heldout per-query read occurred.

The architectural objection is valid: a family that leaves identifier ordering unchanged cannot repair an already measured identifier shortfall. The initial R1/R2 proposal is useful only as a prose-representation control; it is insufficient as the sole next quality attempt. This amendment proposes ONE identifier-capable family, R3, with an explicit general signal and failure/unknown boundaries. It does not claim a target pass.

## Actual frozen DEV source evidence

The audit inspected the existing three ambiguous DEV identifier cases (`bytes`, `put`, `bounded`) and their actual competing declarations. It text-scanned the612,960-byte encoded frozen corpus for call spellings, then inspected source declarations/receiver contexts. This is not an executed binder, graph extractor, feature-vector export or candidate-ranking run. All observed counts would remain lower-bound usage evidence, including zero; no global graph-completeness or intended-domain claim is made. A raw spelling is never certified as a call edge merely because it appeared in that scan.

The following concrete edges are plausible from source; line numbers refer to decoded immutable corpus bodies, not the later runtime source. They are proof examples for a future binder test, not a manufactured training feature table.

A same-compilation-unit-only variant would actually disadvantage ContentAddressedStore.put against DecisionController.put, because the store has no same-unit incoming call. R3 therefore requires the explicitly bounded same-repository cross-file binding/view described in the protocol; it must not silently use local counts as a substitute.

The first two pairs supply a genuinely query-conditioned distinction: distinct enclosing callers of the EXACT member requested by the current query. This is different from document size, number of all calls, project prominence or unconditional file popularity. It could change an identifier ordering. It does not prove intended semantics: a frequently used method may be irrelevant to a user's unstated purpose.

The bytes case remains an informational risk, not a promised fix. Both candidate meanings have multiple genuine callers. If source binding is incomplete, R3 must abstain. Even with all inventoried spellings resolved, caller diversity could tie or prefer the competing implementation. No binding rule, cap or tie-break may be chosen to remove inconvenient real callers. In particular, do not deliberately omit generic/record callers in order to favor SnapshotManifest.

## What is available and what is not

The frozen source contains package/import/type/member declarations, record components, explicit parameter/field types, initializers, method return types and invocation syntax. These support a bounded source-symbol graph without evaluating source. The corpus also contains wildcard static imports (e.g. Registers imports Model.*), `var`, generic collections, lambdas, nested types and overloaded bytes helpers. Unresolved external dependencies, inheritance, dynamic dispatch, ambiguous overloads, method references and incomplete source snapshots prevent a general call graph from being claimed.

The proposed signal uses only a recorded generation's indexed source and the current authorized repository scope. It is not a measure of real production traffic, runtime call frequency, public API importance, external callers, or universal usage. No test/non-test/public/private/static/main/helper preference is learned or applied; private/static information is used only to establish an unambiguous edge/access boundary.

One initial read-only source-printing helper exceeded a requested line range on a shorter file and exited with IndexError. It was corrected to clamp source ranges, then rerun. No model/output was produced by that helper, and no ranking gate is claimed from these inspections.

## Decision for review

The source evidence is sufficient to justify testing ONE usage-capable R3 family with a covered-inventory-or-abstain policy. It does not justify promising that `bytes` or any unseen query will improve. If root rejects the necessary resolver/authorized-graph complexity, the valid alternatives are: retain baseline and report the unresolved quality gate; test explicitly contextual queries as a separately labeled future evaluation (never relabel/replace the frozen80); or obtain a new independently judged corpus with disambiguating intent. An invisible project/role prior is not an alternative.
