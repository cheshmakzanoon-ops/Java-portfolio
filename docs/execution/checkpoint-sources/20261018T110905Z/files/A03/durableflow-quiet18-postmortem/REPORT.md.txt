These are sampled allocation/stack descriptions, not an identified cause of the between-run slowdown or a complete profile of the driver, database, provider or other seven workers.

### Recorded database waits

The streaming parser filters socket events whose start time lies inside the workload's UTC interval, and groups remote address/port. Port 18202 is the configured PostgreSQL endpoint.

| --- | ---: | ---: |
| Recorded events | 173,291 | 219,401 |
| Mean recorded duration, ms | 6.135751 | 9.730842 |
| Nearest-rank p95 recorded duration, ms | 19.539273 | 32.025966 |
| Nearest-rank p99 recorded duration, ms | 76.831588 | 139.539355 |
| Total recorded concurrent duration, seconds | 1,063.270471 | 2,134.956356 |

These are recorded socket events, not SQL statement counts, independent queries, complete request latencies or additive wall time. Multiple threads overlap. Reads at provider port 18201 are sparse (69 / 79); the asynchronous HTTP implementation means their scarcity does **not** prove that provider/network service was cheap or unchanged.

The driver synchronously submits each start and its two signal calls before entering the final completion-poll loop. More than 99.5% of measured elapsed time precedes that loop in both runs. Thus the total throughput boundary is sensitive to submission and database round-trip progress. The published `peakSampledQueueDepth` values 23 / 18 sample only this final loop, not the entire submission phase. The slower DB socket observations support a concrete symptom and an investigation direction; they do not distinguish PostgreSQL lock/query/commit work, storage/WAL/checkpoint behavior, network scheduling or host contention.

## Actionable limits and hypotheses

The strongest supported next investigation is a separate, explicitly identified functional diagnosis of driver start/signal phase durations and PostgreSQL query/lock/commit/I/O waits, with cgroup/pressure/checkpoint observations. Current data has no per-statement latency or server wait samples, so an exact root cause remains unknown. Driver profiling is absent; the retained worker-1 profile cannot substitute for it. Repeated mapper creation and regex compilation are visible in source/profile and could be investigated separately, but this review does not attribute the slowdown to them or authorize changing engine behavior.

Keep the gzip-only capture repair and any later engine investigation distinct. The existing runs are diagnostic old-source observations, not a three-round PASS. All three future repetitions must use one frozen source/runtime/protocol and the unchanged CV ≤10% rule. No averaging, threshold relaxation, held-out-data access, resampling or new performance claim was performed here.
