# Measurement boundary and commands

No performance baseline is accepted until the actual runner output is recorded in evidence. Generator version 2 (`v2-live-identity-shuffled-block`, seed 42006006) uses 1,000,000 commands and 64 accounts. Each shuffled 100-command block contains exactly 60 NEW, 25 CANCEL and 15 REPLACE commands. NEW/REPLACE prices are uniformly distributed integral ticks 9900..10100, with quantities 1..10. NEW orders use GTC without post-only. The configured open-order cap is 100,000. Cancel/replace selects an actual live order and its account/side; only an empty book produces a deliberately missing target. The driver reports both counts, every business outcome, and actual peak/final open orders. The cap is not a claim that the measured book reaches 100,000 orders. Duplicate injections are separately scheduled every 1000 commands, including command zero. Every run verifies the generator's live-order tracker against the engine, checks aggregate cash/inventory and, for durable mode, compares recovered state digests.

Version 1 coupled independently selected accounts and order IDs, producing 39 missing targets in the initial 100-command smoke. It was replaced before collecting any accepted baseline. The new generator has independent assertions across three seeds and 3,000 transitions, including checks that each nonempty-book cancel/replace targets a real account/order/side. The 10,000-command shared-host captures of version 2 had 3,880 live targets and 120 empty-book targets, and a peak of only 18 open orders. These diagnostics validate the driver and capture pipeline; their throughput is ineligible as a baseline.

```bash
projects/06-matchcore/scripts/benchmark.sh core
projects/06-matchcore/scripts/benchmark.sh durable
# Explicit smoke only, never the prescribed acceptance workload:
MATCHCORE_COMMANDS=10000 projects/06-matchcore/scripts/benchmark.sh durable
```

Core driver throughput includes generated command construction, risk, matching, retained outcomes and periodic dedup lookups. Durable driver throughput includes bounded gateway admission, JSON framing, one local `force(true)` per command, immutable aggregate-state publication and acknowledgement. These are separate measurements; memory-only throughput is never durable exchange throughput.

The driver is closed-loop, one outstanding request, and includes scheduled duplicate requests in elapsed wall time. Acknowledgement percentiles exclude generator construction and the separately scheduled duplicates. Closed-loop load has coordinated omission and cannot establish overload latency under arbitrary offered load. Queue depth is a sampled observation, not a full queue histogram. Allocation comes from the JDK ThreadMXBean's live Java thread allocation counters and includes driver/writer/background allocations during the measurement window; allocations from threads already terminated at the end can be missed. Process CPU and GC counter deltas cover this same loop. Heap is a point-in-time used heap, not retained size after GC. Recovery measures only the reopened Gateway constructor after closing the writer, in the same warm JVM with hot OS page cache. It excludes digest comparison and close and is not cold-start or cold-storage recovery.

Each system capture retains its exact JVM command, environment/source identity, bounded GC logs, JFR recording, selected JFR event JSON, stdout/stderr, exit status and resource summary in a unique ignored `.runtime` directory. POSIX child resource accounting covers the entire JVM (including startup, setup and recovery), unlike the measured-loop counters. JFR CPU samples and weighted allocation samples also cover the entire process and are explicitly sampling evidence, not exact method costs. `capture-summary.json` hashes the raw files and summarizes samples without inventing unsampled events. The launchers preserve failed runs. An initial capture failed before launching Java because `/usr/bin/time` was unavailable; the current stdlib resource wrapper removes that dependency.

Prebaseline diagnostic samples showed repeated compilation of the constant identifier regex. The implementation now caches that immutable Pattern; direct malformed-identity/nonmutation tests and the reference suite must pass before final measurement. No speedup is claimed from the shared-host diagnostics.

MatchingBenchmark is a separate JMH partial-fill microbenchmark with three one-second warmup iterations, three one-second measurement iterations and three independent forks (-Xmx512m). Per-invocation setup constructs a two-account resting book outside the timed matching method; setup allocations can affect GC/allocation profilers and are not claimed as matching-only allocation. The system driver measures allocation for its own documented boundary. Run JMH only after the independent reference suite passes.
