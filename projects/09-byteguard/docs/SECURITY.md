# Security and trust model

This is an offline CLI analyzing untrusted classfile bytes under explicit bounds. It has no listening service, authentication layer, tenant state or credential store. The trusted boundary includes the analyzer distribution, JDK, pinned dependencies, rule configuration and owned fixture compiler; target archives remain untrusted. Rule sanitizer entries are assertions about exact descriptors and contexts, not inferred proof of arbitrary sanitizer implementations.

Trusted configuration still has an explicit parsing boundary: 1 MiB rule models and 8 MiB baselines, actual-read limits, depth/token bounds, duplicate-key rejection, and exactly one object. Rule fields and numeric types are checked without coercion; impossible constructors, void-returning sources/sanitizers, duplicate descriptors, and unsupported declarations fail before target parsing. Parse diagnostics omit configuration values. Baselines require ByteGuard's tool/model identity and exact supported-rule fingerprints while retaining ordinary SARIF extension compatibility. Accepting a partial baseline only extracts identities; it does not certify prior coverage. See the [configuration contract](../contracts/CLI.md).

Inputs and dependencies are explicit local paths. No network resolution, target classloader, reflection, Java object deserialization, annotation processing or execution of analyzed bytecode is used. Owned fixture compilation always supplies `-proc:none`. Explicit files, rules and baselines must be regular files; named pipes and devices are refused before opening. ZIP/ZIP64 central-directory metadata is validated against entry/16 MiB bounds before index allocation. Archive entry streams use bounded buffers and never extract; traversal names, duplicate entries/classes, symlinks, nesting, corrupt CRCs and unsupported versions fail with diagnostics. Expanded bytes, per-entry size, CRC and deadlines are checked against actual reads, including directory entries. Case-insensitive manifest discovery rejects ambiguous manifests. Individually selected classfiles share the entry-count budget with directory/archive entries and classpath files. Multi-release selection follows manifest semantics rather than counting all variants as application classes.

Parsing and analysis have independent structural/state limits as well as a shared work/deadline budget. Iterative hierarchy, SCC and heap-alias traversals avoid recursion proportional to an adversarial inheritance/call/reference chain. Native dispatch alternatives remain visible alongside modeled overrides. Unknown/native calls conservatively propagate uncertainty to returns and reference receiver/argument contents, including void calls; mutable opaque returns preserve later stores and possible operand aliases. Unsupported bootstrap/lambda effects retain explicit partial coverage. Unknown is distinct from clean bottom.

The CLI writes caller-selected report/explanation paths and project-local demo/benchmark state. Reports must be outside scanned directories and cannot alias explicit inputs, classpath files, rule models, or baselines; checks include existing hard links and symbolic parent directories. Unsafe destinations are rejected before scanning and never receive an error report. SARIF, JSON and every explanation DOT use a sibling temporary file before replacement, preserving an earlier output if serialization fails. Symbolic output entries are refused; atomic replacement of a hard link preserves the linked input inode. Supply output paths the caller owns and keep explanation directories free of untrusted pre-existing files. These checks do not protect against another process racing filesystem changes. Source metadata is sanitized for SARIF; absolute workstation paths and source contents are not embedded as routine finding evidence. Do not put secrets into rule files or archive names. Reports may expose method names, source basenames, modeled source/sink descriptors and instruction identities; treat reports according to the sensitivity of the analyzed program.

The pinned SARIF2.1 schema and upstream license are preserved under `contracts/`; tests validate actual complete, error and partial reports. Internal source identities use length-prefixed method names; report hashes use an unambiguous lossless tuple for delimiter/unpaired UTF-16 names, so legal JVM punctuation cannot merge distinct witnesses. Existing ordinary finding fingerprints remain stable. Baselines use exact finding fingerprints, with no broad filename suppression. Every resource-limited scan exposes terminal status and machine-readable unfinished coverage.

This project does not claim a complete verifier, universal soundness, exploitation proof, filesystem race protection or safe execution of target code. Path fixture validation is lexical and assumes an owned symlink-free root. Weak object-insensitive heap aliases and coarse shell-array modeling have reproduced false positives outside the preregistered corpus. Details, concrete controls and unsupported behaviors are in [THREAT-MODEL.md](THREAT-MODEL.md), [INVARIANTS.md](INVARIANTS.md) and [REVIEW.md](REVIEW.md). An empty result must never be advertised as security certification.
