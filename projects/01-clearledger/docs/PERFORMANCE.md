# Performance methodology

The prescribed generator creates100000 journals across20 tenants and10000 accounts with seed20261017, CAD/USD/JPY, 20% four-line journals, duplicate retries every100 inputs and reversals every1000 (100000 original journals plus100 reversal journals and1000 duplicate submissions in the full run). It computes expected balances with the independent reference before invoking SQL and writes `target/benchmark/rN-wN/expected-balances.csv`.

Run `scripts/benchmark.sh 100000 3` on an otherwise idle host. It builds first, then runs1/8/32 bounded Hikari writer pools in three fresh-database rounds. Raw latency CSVs and result envelopes live under target/benchmark. `scripts/benchmark.sh 1000 1` is a smoke run and cannot satisfy the full workload gate.

Measured boundary: closed-loop JDBC transactions including all same-key transaction/client retries, their backoff, and duplicate/reversal work associated with each input. Production transactions have a 12-attempt serialization budget; the workload client permits at most six calls per operation and retries only temporary responses. Temporary responses, additional calls and exhausted client budgets have separate counters. Any exhausted budget fails the run. `client-outcomes.json` records completed/failed input groups even when the driver fails. Results report throughput, p50/p95/p99, elapsed time, retry count, sampled concurrent lock waiters, reporting backlog/replay duration, sampled peak Java heap, separate whole-child process CPU/RSS/context switches, JFR CPU/GC/heap/allocation samples, JVM flags and runtime, CPU, cores, cgroup limit and relevant database durability settings. The database and clients share the host; the API network path is excluded. There is no separated warmup because writes use a fresh durable dataset. Closed-loop latency underestimates open-loop overload queue delay. Lock waiter counts are sampled observations, not aggregate wait-duration measurements; sampled Java heap is not process RSS. Do not infer production capacity.

See STATUS and committed evidence for exactly which measurements were actually run. Deliberate per-period lock serialization is an expected scaling bottleneck; the full scaling study remains unrun. Reducing that serialization requires a new close/post proof rather than removing the fence for a prettier number.

The first shared-host 1,000-input system smoke passed writer 1 and failed writer 8 on an actual temporary serialization exhaustion during reversal; writer 32 was not reached. Raw failed-run artifacts are retained under `.work/A01/system-smoke-first-failed/`. This prompted the bounded same-key client retry correction. The corrected shared-host smoke subsequently passed 1/8/32 writers with all independent balance, SQL and replay checks. The 32-writer run observed 24 temporary client responses, 24 same-key additional calls and zero exhausted budgets. See `evidence/system-smoke-current.json`; this bounded functional success does not satisfy the full workload gate, and the failed run remains diagnostic evidence.

CPU microbenchmarks use JMH 1.37 for exact money parsing and canonical digest computation with 2/100 journal lines. The full command is `scripts/microbenchmark.sh full`: three independent JVM forks, three one-second warmups and five one-second measurements per case, one thread, returned values consumed by JMH, and GC allocation profiling. The smoke uses one fork and 100 ms iterations and proves execution only. Both retain raw JSON, console and environment manifests under `target/microbenchmark/`. Before an isolated measurement reservation, prepare normally; `scripts/microbenchmark.sh full --prepared` then verifies exact source/artifact hashes and runs without Maven. A missing or stale marker fails rather than silently building during the quiet phase. The workload offers the same fail-fast behavior through `scripts/benchmark.sh 100000 3 --prepared`. These caches never substitute for ordinary unit/integration verification.

`capture-environment.py` records source/root POM hashes, dependency pins, JDK and JVM context, CPU/cgroup/memory, database image and running containers without credential values. `summarize-performance.py` refuses a full acceptance summary until all nine 100,000-input runs have matching source/seed/independent expected balances, 20 touched tenants, 10,000 touched accounts, positive per-input latencies, successful SQL cardinality/backlog checks and actual JFR CPU events. The published per-writer summary includes all three observations, mean, sample standard deviation and range. No measurements are currently claimed as quiet-host acceptance results.

The full summary distinguishes **101,100 planned logical client calls** (100,000 originals, 1,000 deliberate duplicate requests and 100 reversals) from **actual client-call attempts**, derived per run by adding the driver's measured additional-call counter. Internal transaction retries are reported separately. These fields do not claim an exact SQL statement count.
