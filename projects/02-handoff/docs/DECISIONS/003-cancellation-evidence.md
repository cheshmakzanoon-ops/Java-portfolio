# ADR 003: recorded cancellation evidence is semantics 3

The expanded independent review found a mismatch: typed semantics 2 accepted STARTED→FAILED→CANCELLED in pure replay for a lone failed root, while the live store rejects cancellation of terminal FAILED. A blanket failure-set check would also reject legitimate cancellation: another parallel worker may still own a forward lease, so the live store materializes CANCEL_REQUESTED while that worker settles. Claims and lease barriers are durable task-table state and were not recorded in the earlier cancellation event.

Semantics 3 records the database observation as a typed input. Under the instance lock, cancellation counts current LEASED forward tasks and appends CANCELLED with one actual INTEGER value in `result`. The count is0..128, and replay rejects counts exceeding eligible unsettled forward activities. No workflow node consumes this administrative value. A failure is terminal for cancellation when no unknown outcome, uncompensated recorded completion, or recorded forward lease remains. Failed compensation stays visible and may retain a cancellation intent; successful late forward completion still creates its compensation obligation. The persistence lease barrier continues to wait for outstanding forward credentials before undo.

This evidence counts current database leases. It does not prove that expired workers or previously authorized external calls have stopped. Cancellation remains cooperative; provider idempotency, fencing, uncertainty and reconciliation keep their existing guarantees.

The change explicitly pins a new interpreter version. `LegacyInterpreterV2` freezes the prior typed interpreter, while `LegacyInterpreterV1` retains the original String format. Existing definition and instance pins remain1 or2; their histories, cancellation payloads, hashes and worker parameters are not rewritten. Semantics2 CANCELLED records retain their empty result payload and original interpretation, including ambiguity when examining a malformed history without its durable task records. Its live store still rejects terminal cancellation. New semantics3 histories require the typed cancellation evidence and reject the confirmed terminal-failure transition.

The definition format and compiled activity/type signatures are unchanged from2; only cancellation evidence/replay validation changes. Redeploying an existing immutable definition preserves its existing pin. A higher definition version or new definition is required to activate3. The store and SDK retain handlers for all three supported pins. The existing typed JSON history column can encode the new INTEGER evidence; no schema rewrite or Flyway checksum change is needed.

A real PostgreSQL regression seeds a persisted typed2 definition, applies an independently logged effect while its claim remains leased, fails the parallel peer, cancels, and deploys3 without changing the old history/hash/pin. It then acknowledges the late effect and compensates. The same case under3 requires recorded lease count1. A separate terminal-failure path verifies that rejected cancellation changes neither history nor version. Pure tests cover terminal FAILED before and after successful compensation, impossible/missing evidence, and the permitted late-completion path. Latest outcomes and fingerprints belong in STATUS; the presence of this ADR is not a pass claim.
