# Trust and security

Workflows are untrusted finite JSON data, never uploaded executable code. The DSL accepts a small equality grammar and a compiled activity registry. A caller cannot supply provider URLs, redirect destinations, shells, reflection targets, JARs, or expression engines. Trusted workers have database access and generation-bearing per-claim credentials; this is not a hostile-worker sandbox. Provider endpoints are deployment configuration. The transport accepts only an HTTP(S) `/effects` endpoint without embedded credentials, query parameters, or fragments. Redirects are neither followed nor accepted as completed effects. Only the trusted provider's HTTP 503 response with `X-Effect-Outcome: NOT_APPLIED` is a definitive pre-effect refusal. Other errors remain uncertain because an HTTP status alone cannot establish whether an effect occurred. Responses are limited to 4 KiB before buffering and decoded as strict UTF-8; oversized or malformed receipts remain uncertain failures rather than successful results. The fake provider accepts synthetic local data and binds loopback.

The default protected profile validates signed JWTs against a configured OIDC issuer's JWKS, issuer, audience, required expiry, subject and tenant. After cryptographic validation it checks the original signed JWS payload JSON, preventing Nimbus claim conversion from silently changing numeric subjects into strings. Payload size, nesting, duplicate keys and original claim types are bounded. Authentication filters and controller failures return RFC9457 problem bodies. Viewer, operator, deployer and worker scopes are distinct; SQL reads/mutations scope every execution to its authenticated tenant. Worker mutations also compare request tenant and stored task attributes. Integration tests use a real local issuer with generated RSA keys to test valid and forged signatures, wrong issuer/audience, expiry, role and cross-tenant access. No actual issuer secret is committed.

The explicitly named dev profile uses HTTP Basic disposable accounts and rejects non-loopback server binding. Demo credentials are synthetic, not production passwords. Production deployments need TLS ingress, credential rotation, database transport policy and an authenticated provider; this portfolio's local trusted profile does not claim those operational certifications.

Public HTTP requests, including worker claim requests, are capped at 8 KiB including chunked input. The four worker acknowledgement routes (dispatch, heartbeat, complete, and fail) accept up to 528 KiB because they echo an issued claim containing serialized task inputs. A persisted task input is capped at 256 KiB; JSON string escaping can double that size, and 16 KiB covers the bounded result, identifiers, reason, and framing. Every echoed attribute, including the entire serialized input, must match the authoritative leased task. A larger body grants no execution authority. The maximum legal fan-in/arity case is exercised through authenticated HTTP, including quote-heavy near-cap inputs, tampered claims, and chunked over-limit requests.

The local provider accepts at most the task-input byte budget plus the longest compiled activity name and its separator. Its response cap remains 4 KiB. The large-task regression executes an actual provider request after authoritative dispatch, verifies duplicate-key delivery creates one independent effect, and persists that receipt through the worker API. A separate boundary test checks exact-limit acceptance, over-limit refusal without an effect, and retained idempotency after provider restart.

Definitions cap 128 nodes and 16-way fanout; starts cap 32 input fields/4 KiB; results cap 4 KiB; history caps 10,000 events. Active executions and queued tasks have tenant quotas. SQL uses parameters and statement timeouts. Results/signals reject credential-shaped secret fields/text, including markers in multiline text, and oversized content, and diagnostics omit token values and stack traces. Marker screening is a guardrail, not a general secret detector. Do not place secrets in workflow business inputs. Operator reasons are business evidence and must not contain credentials. [WorkflowLimits](../workflow-model/src/main/java/io/github/cheshmakzanoon/portfolio/durableflow/WorkflowLimits.java) defines the shared byte budgets; body limits apply before JSON parsing.

Known boundary: authorization protects API callers. PostgreSQL and local process owners are trusted and can inspect/edit the demonstration database or provider log. No claim of tamper-evident audit storage, hostile multitenant worker isolation, automatic security certification or internet-safe Basic authentication is made.
