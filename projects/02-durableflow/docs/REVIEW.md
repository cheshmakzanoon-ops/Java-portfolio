# Design review record

Reviews concentrate on boundaries that can create inconsistent history or duplicate external effects. The findings below describe development defects and their regression coverage; they are not production incident reports.

| Finding | Correction and regression coverage |
| --- | --- |
| The same current lease could authorize a non-idempotent call twice. | Dispatch intent uses a compare-and-set; independent provider `CALL` and `EFFECT` records check that repeated authorization is refused. |
| Compensation could be attached to a non-activity node without a safety contract. | Definition validation rejects unsupported compensation targets. |
| Default JWT timestamp validation did not require expiry, and registered-claim conversion could coerce subjects. | Required original claim types and expiry are checked after signature verification; HTTP tests cover missing claims, wrong types, forged signatures, scope, and tenant boundaries. |
| Cancellation could select compensation before another forward lease acknowledged its result. | Cancellation waits for forward leases to settle, preserving reverse recorded-completion order. |
| Replay could accept unknown task identities or a terminal failure cancellation that the store rejected. | Replay validates task identity and transition legality. Semantics version 3 records a bounded forward-lease observation; frozen versions 1 and 2 retain their historical behavior. See [ADR 003](DECISIONS/003-cancellation-evidence.md). |
| Startup failures leaked acquired containers/processes, and PID-only shutdown could select a reused PID. | Startup builds first, snapshots existing container identities/state, and rolls back only new acquisitions. Boot/start identity, exact role/artifact arguments and pidfd rechecks authorize signals. Ten real-JVM/fake-Compose cases cover partial startup, prior-service preservation, failed ownership checks, and procfs exit interleavings and restricted executable observations. |
| Prepared artifacts could be rebuilt while an older runtime remained live. | Preparation refuses owned live processes, including those with missing PID files, and binds source, JARs, and verification evidence before startup. |
| A rollback or connection-close failure could hide the command that caused cleanup. | `JdbcTransactions` owns resource cleanup and preserves the primary failure, including commit uncertainty, with cleanup failures suppressed. Fault-injected JDBC tests check call order and exception identity. |
| A full history in one scheduler batch could roll back unrelated executions; a later command could inherit stale deferral metadata. | `SchedulerBatch` uses one locked transaction per instance; additive migration V3 records bounded retry admission with a version comparison after rollback. PostgreSQL tests check independent progress, locked-row skipping, restart persistence, and an intervening successful cancellation. |
| Current replay selected reverse compensation correctly but could accept an event naming an older obligation. | Replay checks every compensation event against the next outstanding reverse-completion obligation. Tests include out-of-order completion, dispatch, failure, and uncertainty. Frozen interpreters remain unchanged. |
| Shutdown could stop heartbeats and provider resources before accepted work persisted a receipt. | Worker shutdown drains accepted work with lease resources alive, bounds interruption, and restores the caller's interrupt flag. A provider barrier test separates committed effect from delayed acknowledgement. |
| A temporary database failure during claim acquisition could terminate the worker, while blanket retry could hide permanent schema errors. | Explicit recoverability classification drives bounded, interruptible retry in workers and schedulers. Tests cover recovery without speculative dispatch, shutdown during backoff, SQL failure after the instance lock, and visible terminal SQL/contract errors. |
| A valid large task input could exceed the public request cap when echoed inside a worker claim, or the provider's old 4 KiB request limit. | Shared byte budgets account for duplicated predecessor data, JSON string escaping, and the compiled provider prefix. The authenticated maximum-fan-in/arity test follows dispatch, provider delivery/deduplication, and receipt completion; boundary tests cover tampering, oversize refusal, and restart. Public commands retain their 8 KiB bound. |

These historical scopes do not certify later changes. Original [verification evidence](../evidence/verification.json) and [prepared-build evidence](../evidence/preparation-verification.json) remain available.

The current transport review additionally addresses unbounded provider responses, redirect acknowledgements, malformed receipt encoding, and credential markers hidden by line separators. The new tests use actual loopback HTTP exchanges for both fixed-length and chunked responses. Current executed results belong in [verification status](STATUS.md).

The runtime review follows every production class and all three schema migrations: finite graph/value validation; current and frozen replay; history serialization and instance transactions; claims, lease expiry and dispatch fencing; timer/signal races; cancellation, compensation and operator resolution; provider persistence/transport; API authentication and bounds; runtime ownership and verification drivers. The persistence decomposition separates transaction ownership, history, version adaptation, failure policy, and scheduler batching while preserving the public store commands and stored interpreter pins. [Architecture](ARCHITECTURE.md), [invariants](INVARIANTS.md), and [operations](OPERATIONS.md) describe those boundaries and their failure paths.

Review coverage is finite. It does not establish a production threat assessment, full reference performance baseline, or successful hosted release pipeline.
