# Wave3 declaration-membership interpretation (before execution)

The two frozen `.work/A07` design packets remain unchanged. Root accepted A06's static review finding: R3's whole-query unknown bypass covers exact-declaration SUBSET MEMBERSHIP, not only the usage of known declarations.

Before any R3 subset sort, every R0 candidate must have a positively observed, bounded inventory of all declarations matching the actual query. An unsupported/oversize/malformed candidate potentially declares that name and forces the ENTIRE query's exact R0 ordering. It cannot be treated as an incidental mention merely because its AST is unavailable. Proven saturation32 for a known target resolves only capped count uncertainty; it never establishes any other candidate's subset membership.

Required direct counterfactuals: two eligible positive-count private helpers plus one unsupported candidate; and a known saturated target plus that unsupported candidate. Both preserve the whole original order. These rules are part of the eventual versioned protocol/schema/source freeze, before feature export or scores; they add no candidate family or tuned threshold.

Canonical graph-content bytes contain stable source/member identities and source hashes, not random generation IDs. The outer immutable commit binding records the generation/graph checksum. Identical indexed source yields identical graph bytes across generation IDs; leases, scope, Access version, model/schema and the outer generation still bind serving/cache/cursor operations.

Implementation, compilation and all wave3 metrics are NOT_RUN at this addendum's creation. Source-only implementation was authorized while quiet12 prohibits all Java/Maven/evaluation/training/queues.
