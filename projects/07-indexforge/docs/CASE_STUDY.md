# Transactional search as an application problem

Lucene already solves inverted indexing and BM25. IndexForge focuses on the lifecycle surrounding it: immutable input identity, safe bounded acquisition, complete snapshot construction, durable publication and per-request snapshot lifetime. A search that combines new counts with old snippets is incorrect even when both Lucene readers are individually valid. The application therefore leases one committed generation for all response components and publishes only a warmed committed reader through a checksummed atomic pointer.

The initial10,000-record retry test exposed a canonicalization defect: manifest hashing serialized entries in sorted order, while the in-memory record retained input order. Reloading a durable manifest returned the same job identity but a differently ordered object. Canonicalizing the immutable constructor aligns serialization, equality and retry behavior; the test remains as regression coverage.

The first authored relevance smoke corpus had empty illustrative methods and literal topic-heading queries. Independent coordinator review rejected it before any ranking measurement. V1 is retained with its hashes and disposition; v2 froze complete substantive original source with provenance, near-topic distractors and paraphrased requests. Independent review then removed16 unsupported supporting labels before metrics, freezing v3. Preliminary development/validation results show modest nDCG gains but worse reciprocal rank; failures remain published and held-out stays unopened until a fixed decision. This prevents tuning/relabeling a toy corpus into an impressive but misleading score. The held-out selection protocol is executable and refuses held-out measurement before a development decision exists.

The real HTTP integration also caught an adapter error: `sendError(413)` on an oversized body triggered protected ERROR redispatch and returned401. A direct bounded JSON413 response fixes the public status without weakening endpoint authorization. A separate concurrency regression showed that synchronizing whole replacement builds on the engine blocked new requests from acquiring the still-valid old generation; per-tenant writer locks now keep the generation-map lock short, and a latch-controlled test proves old search completes before the build is released.

Tradeoffs are deliberate and visible: replacement indexes cost disk/build work but make snapshot visibility simple; current and previous generations are retained for fallback, old readers close only after leases; cursors expire or return410 after retirement instead of pinning generations indefinitely. The application response cache includes the access context and always rechecks current permissions. Search scope is local configured snapshots, with bounded query grammar and candidate windows.

See STATUS for executed evidence and remaining acceptance gaps. No production users, uptime, universal relevance quality or independently verified power-loss behavior is implied by this portfolio project.

Independent A06 review found that atomic snapshot visibility alone did not guarantee durable job idempotency: jobA could publish its pointer, fail before writing its completion marker, then be resumed after successful jobB and overwrite B with stale A. The repair puts immutable job identity in committed metadata and reconciles the currently published job into a checksummed completion receipt before another tenant job can publish, including on restart. The direct regression covers AFTER_POINTER and RETIRE faults, both live retry and restart, and asserts B's exact generation/content survive A's later resume. Corrupt receipts fail explicitly instead of becoming false completion. Final verification status remains in STATUS.

The same review exposed a path-identity ambiguity: a root snapshot called a document `src/Foo.java`, whereas selecting that file alone rebased it to `Foo.java`. Paths now stay relative to the configured repository source root for all directory/file selections; a full-root → nested-file → nested-directory regression checks one stable key through replacement.

A further confidentiality review distinguished access filtering from collection statistics. Raw Lucene explanations included n/N/avgdl from a tenant reader containing denied repositories. The public explanation now summarizes matching authorized-document features, final score and explicit rerank bonuses, without returning raw collection statistics. BM25 scores/order still depend on tenant-reader statistics; SECURITY records that residual statistical channel explicitly. This is a narrower and testable confidentiality claim than promising complete information noninterference from a Boolean filter.
