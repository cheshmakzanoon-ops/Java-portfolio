# Security boundaries

The local demonstration generates a 30-day disposable self-signed certificate with localhost SAN and separate random 256-bit credentials for each peer ID, clients and administration. TLS 1.3 uses JDK libraries; clients validate the generated certificate and HTTPS endpoint identity. No TLS verification is disabled. Secrets live only in ignored local files; the authentication properties file is owner-readable/writable. Member processes necessarily share a local owner and trust domain. A malicious process with filesystem access can steal credentials or corrupt storage, outside this non-Byzantine model.

A versioned envelope supplies cluster ID, source/destination ID, role credential, request correlation and typed body. Credentials compare in constant time. A peer credential permits only protocol messages, the client credential only GET/mutations, and the admin credential only status/partition/heal/snapshot. Unknown cluster IDs, invalid roles, malformed enums, trailing bytes and oversized frames reject. Netty checks the 512-KiB length limit before allocating the frame; nested counts and key/value/chunk lengths are also checked before allocation. No arbitrary Java object deserialization exists.

Every listener binds loopback. Administration is deliberately local and destructive partition controls are demo-only, separately authenticated. This implementation does not offer remote public hosting, authorization by individual key, rotating identities or production certificate provisioning. The generated certificate/credential directory is trusted local configuration, not a production PKI. Three fixed members are assumed non-Byzantine; a credentialed malicious member can violate the protocol's assumptions.

Bounds limit connections, state-machine events, pending commands/reads, outbound channel watermarks, replication records, keys, values, clients and retained key/value bytes. Network overload may drop peer packets; clients receive explicit resource exhaustion when admitted enough to respond, otherwise a bounded transport timeout. Snapshot/WAL generations retain the current and previous recovery paths; monitor free disk space and the 64-MiB per-record limit.


## Recovery input validation

Checksums detect accidental corruption; they do not authenticate local storage. Recovery additionally validates the structure and meaning of a checksum-valid snapshot. Snapshot index/term coordinates must be nonnegative and agree on the empty-state boundary. The persisted vote must identify a fixed member or the unset sentinel, and the current term must cover the snapshot term.

Retry receipts are part of the consistency boundary. Each client ID must satisfy the same limits as a live mutation; duplicate IDs are rejected rather than overwritten. A receipt requires a positive sequence, an exact 32-byte SHA-256 digest and a committed `OK` or `CAS_MISMATCH` result. Malformed snapshots and WAL state fail with an `IOException` before becoming active. Recovery never repairs an ambiguous client history by dropping a receipt. Network snapshot installation also rejects a last-included term above the current RPC term before changing active state; a malformed transfer cannot force the persistence layer to activate an impossible term history.
