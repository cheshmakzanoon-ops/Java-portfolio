# Reproducible workload

`./projects/03-quorumkv/scripts/benchmark.sh` executes 100,000 operations per combination for 1, 8 and 32 clients, 90%-read/10%-PUT and 50%-read/50%-PUT profiles, three independent runs. Each scenario starts three actual JVMs with independent durable directories, JDK TLS, and flush-on-every-state-transaction. Values are 1,024 bytes over 128 bounded keys; seed 42 controls choices. Per-client mutation identities are serialized. The boundary includes client TLS round-trip, Raft replication, disk flush and read quorum confirmation.

The load is closed-loop: latency samples omit operations a stalled client could otherwise have offered (coordinated omission). Do not use these samples to claim open-loop overload behavior. Throughput, p50/p95/p99, error count, client GC counts/time, sampled and end-of-run replication lag with sample/error counts, client/member CPU time, load-worker allocated bytes, last storage snapshot duration, member GC logs, bounded JFR recordings and runtime metadata are saved beside raw CSV. The environment/source fingerprint is recorded. The separately asserted fault demo reports election/recovery and snapshot observations; snapshot wait time is distinct from the storage worker's measured snapshot publication duration. JFR is enabled for the measured run and its overhead is included; allocation counters cover load-worker threads, while JFR includes member allocation samples.

`--smoke` uses 100 operations per combination and one run. It proves the driver exercises real behavior and is explicitly insufficient for P03-A5. Shared-runner measurements are noisy; run prescribed performance scenarios without concurrent compilation and report variability across the three runs. No quantitative guarantee has been promised. Current execution evidence and remaining measurement gaps are recorded in STATUS.
