# Reproducible measurements

`scripts/benchmark.sh` runs only after the full real stack is healthy and other builds/stacks are quiescent. It seeds **50 tenants × 200 active rules × 200 policy revisions × 100 roles per revision × 1000 resources per tenant**, not a reduced in-memory substitute. Policies include department/clearance allow and explicit suspension deny, with 20% mismatched-department resource denials. The workload records a source tree fingerprint and uses seed 20261018. Its decision boundary is authenticated HTTP -> JWT verification -> tenant snapshot -> versioned cache -> evaluation -> mandatory committed PostgreSQL audit -> response. Keycloak token issuance happens before measurement; signature verification still occurs per request.

Three independent HTTP runs each use 1000 warmup requests, then 100000 timed decisions with 16 closed-loop clients. Hikari has eight connections; decision service has a 64-request bound and 500-entry AST cache. The driver records actual throughput, p50/p95/p99 latency, SQL prepared-statement count (including telemetry reads), cache size, expected/observed denials, errors, and maximum client in-flight. Closed-loop load suffers coordinated omission: it understates latency under stalls. No aggressive latency CI threshold is enforced. The driver captures separate decision-service and client JFR recordings. Server summaries report observed CPU samples, GC events and explicitly estimated allocation sample weight; JMH reports exact profiler-normalized allocation for its component boundary. Raw JFR recordings remain ignored under `.work/A05/runtime`; JSON result envelopes are small committed evidence when real measurements finish.

JMH uses three forks, three one-second warmups and three one-second measurement iterations, consumes returned policy/decision objects and reports SampleTime microseconds plus GC allocation. It measures cold compilation and warm indexed evaluation separately from the authenticated database path. These numbers must never be represented as network/database latency.

At this checkpoint performance results are pending. No throughput or latency result is claimed until evidence contains completed runs and the reference-machine manifest. `benchmark-smoke.sh` uses the real full seed but a reduced request count; it is explicitly not the acceptance workload. CPU/GC observations must come from JFR/JMH output, not invented estimates. Before/after tuning requires identical workload/host and three independent runs; this is a baseline until such a comparison exists.

The HTTP load driver fails on unsuccessful warmup, uses ten-second network request deadlines and a single fifteen-minute measured-workload deadline, then interrupts workers and waits at most fifteen seconds for cancellation. Timeouts fail the run rather than producing a successful partial envelope.

The runtime is now prepared without starting services: successful unchanged-source default verification is bound to three executable JAR hashes, and each extracted class/dependency is checked against its packaged bytes. Eight actual stale/tamper/restoration checks passed. During the reference reservation, `TENANTSHIELD_NO_MAVEN=1` prevents a surprise rebuild. The coordinator's prepared protocol is `.work/A05/run-reference-window.sh`, gated by explicit `TENANTSHIELD_QUIET_GRANTED=1`; it has not been executed. Image pins select the exact previously tested PostgreSQL/Keycloak artifacts. These preparation facts are not throughput, latency or allocation measurements.
