# Case study: revocation without stale allow caches

The problem is a fictional document SaaS with tenant-local role inheritance and resource-owned attributes. A good explanation must show why the exact snapshot authorized a request, and a revoked principal must not retain access through a warmed cache.

The central choice is to cache only immutable compiled ASTs and never membership decisions. Every operation still obtains a PostgreSQL repeatable-read snapshot and its tenant epoch, current membership, active version and resource attributes. This makes the guarantee precise at snapshot establishment, at the cost of a database dependency and committed audit work per request. Monotonic policy versions and epochs make stale publication and rollback observable.

The original recursive-descent parser type-checks a small language with explicit bounds. An independent, eager unindexed AST interpreter is used as an oracle for seeded generated expressions and whole policy decisions. Generated testing exposed a defect in the oracle's nested Java ternary: UNKNOWN could be unboxed to boolean. Replacing that with explicit truth branches fixed the oracle; the production Truth enum did not share that defect. This is why the tests compare independently expressed semantics instead of merely calling both code paths with canned success conditions.

RLS protects accidental missing tenant predicates while transaction-local settings prevent pooled connection state from escaping. Server-owned membership/resource fields cannot be overwritten through caller context. Local Keycloak demonstrates genuine JWT verification; fake JWT headers are not identity. The protected resource makes a fresh decision per operation and refuses dependency errors.

Evidence and remaining gates are in STATUS. No production customers, deployments, security certification, commercial uptime or employment history are claimed. Distributed cancellation of already authorized writes and a universal authorization language are outside scope.

The first fully executing integration suite found a consequential PostgreSQL lock defect: two of nine scenarios errored, while the other seven passed. Administrative mutations took `FOR UPDATE` on the tenant epoch row. That stronger lock changed how an older repeatable-read transaction's audit foreign-key `FOR KEY SHARE` lookup followed the updated parent tuple, causing SQLSTATE 40001 after revocation and HTTP 409 for concurrent publication readers. A minimal real PostgreSQL 18.3 schedule reproduced the precise FK query and failure; the same schedule committed its old-snapshot audit with `FOR NO KEY UPDATE` instead. The chosen fix keeps administrative writers serialized while permitting FK key-share checks, since no administrative mutation changes tenant identity. No decision retry, duplicate audit write, weakened consistency level or relaxed concurrency assertion was introduced. The existing held-snapshot and alternating-content publication integration tests are the regression gates; their corrected full run passed all nine integration methods unchanged at 01:29:50 UTC (see STATUS).
